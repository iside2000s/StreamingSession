日期：2026-10-29。运行标识：`20261029-043809-793`。Windows 电脑使用 RTX 5070、CloudXR Runtime 6.2.3 和 Stream Manager 6.1.0。两台设备使用已经安装的 visionOS 客户端，本次没有编译或修改客户端。

## 第二轮复测：交换连接顺序仍然失败

运行标识：`20261029-060841-144`。用户确认两台不能同时看到画面和转头：一台正在观看时，另一台扫描配对二维码后无法进入画面。

- 14:09:30，B 连接成功。14:09:43，A 配对进入 `WAITING` 后断开；A 日志记录 47999/47998 绑定失败、Windows `10048` 和无法创建视频 RTP transport。
- 14:10:15，A 连接成功。14:10:29，B 配对进入 `WAITING` 后断开；B 日志出现同样的 47999/47998 冲突和视频 RTP transport 创建失败。

这轮将顺序交换后仍可复现，确认当前实现只能轮流使用。扫码请求已经到达各自配对服务；实际失败发生在 SDK 创建原生媒体传输时。第二轮服务仍保留供用户复测，由启动脚本按原定时限自动清理。

## 第三轮：ICE 自动模式仍然失败

运行标识：`20261029-061811-471`。公开 C API 探针确认 `apple-vision-pro` profile 接受并读回 `enable-ice=true`、`media-port=0`。A/B 启动日志也明确记录 `backendMode: nvst-native`、`enableIce: true`、`mediaPort: 0`。

- 14:19:17，A 连接成功。
- 14:19:33，B 连接失败，仍在 UDP 47999/47998 报 Windows `10048`，随后无法创建视频 RTP transport。
- 14:20:05，A 断开后，B 连接成功。
- 用户确认这次仍然只能一台有画面。

因此已验证的两个网络配置模式都没有实现原生媒体端口隔离。后续调查转向 [进程容器网络与 GPU 探针](../cloudxr-network-isolation/README.md)，容器内 NVENC 和实际串流仍未验证。

## 第一轮关键证据

以下时间均为电脑当地时间 UTC+8；原始日志保留在忽略的 `state/` 中，不提交认证材料或设备地址。

- 12:39:52，A 的会话为 `CONNECTED`，SDK `headset=True`。用户确认看到示例画面。
- 12:42:26，B 的会话为 `CONNECTED`，SDK `headset=True`。
- 12:43:21，A 恢复连接；当时 B 已暂停。
- 12:44:16，B 恢复连接；当时 A 已暂停。
- 12:44:31，B 仍连接时，A 恢复失败。A 的 SDK 日志记录 UDP 47999 和 47998 绑定 `0.0.0.0` 失败，Windows 错误 `10048`。随后为 `Unable to create RTP transport for video stream 0`，并报告握手失败。
- 12:44:55，A 再次配对重试，重复同样的端口冲突和视频传输失败。
- 检查 UDP 端点时，47998、47999、48005、48008、48012 都由 B 的运行时进程持有。A 没有对应媒体端点。

A/B 分别设置了 `mediaPort: 50120` 和 `mediaPort: 50220`，但观察到的 Apple 原生视频端口仍是上述固定端口。设置不同 `serverPort` 确实隔离了 TCP 信令；不能据此推断媒体也完成隔离。

A 的 SDK 日志明确记录 `Using public endpoint` 和 `fixed media port 50120`，说明自定义媒体端口已经被接受；随后创建原生视频传输仍然尝试绑定 47998。问题不能归结为忘记传入配置文件。

## 构建和检查

WPF 实验程序、C# 信令中继和 C++ OpenXR 方块示例构建成功。真实 TCP 集成检查通过：两路源地址路由、16384 字节二进制内容、半关闭后的反向响应，以及未知和重复源地址拒绝。PowerShell 脚本语法检查通过，状态脚本正确提取了 A 的 47998/47999 冲突。

测试结束后，本次启动的管理器、运行时和中继均已退出，原有单用户程序仍在运行。三个核心 SDK DLL 的 SHA-256 与基础实验记录一致。运行时另有 `Unsupported GPU detected` 提示；本次结果不构成对 RTX 5070 或双路性能的支持性认证。

## 结论与后续约束

临时目录、RPC 管道和信令隔离足以让两套运行时并行启动，但本次并未完成一台电脑同时服务两台 Vision Pro。当前阻碍位于 SDK 原生媒体传输层，单纯多开窗口或修改现有 YAML 的 `mediaPort` 无法解决已观察到的冲突。

[官方网络文档](https://docs.nvidia.com/cloudxr-sdk/latest/requirement/network_setup.html)分别列出了 Apple 原生客户端的视频端口和 WebRTC 媒体端口。[管理 API 文档](https://docs.nvidia.com/cloudxr-sdk/latest/usr_guide/cloudxr_runtime/runtime_mgmt_api.html)提供 `media-port` 属性，但公开说明没有提供本次所需的多个原生视频端口逐路映射接口。本记录不推断其他 SDK 版本或未公开配置一定不可行。

继续推进需要找到经真机验证的原生媒体端口配置能力，或为每路提供独立的操作系统网络环境。后者还需要另行验证 GPU、编码和客户端可达性，不能将其视为已经可用的替代实现。解决串流隔离后，仍须独立开发 Unity 多人同步和共享空间对齐。

本实验没有修改 SDK DLL、机器级 OpenXR 注册表、系统环境变量、网卡或防火墙。原始项目目录、Unity 项目和 visionOS 客户端源码保持本次实验前的状态。
